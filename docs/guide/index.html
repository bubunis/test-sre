    Token Service: the reviewer's lab

    A guided tour of the assignment, in the order I'd show it. Each mission says how long it takes, what to run, what you should see, and why it's built that way. Everything runs on one laptop: Docker Compose first, then a three-node Kubernetes cluster (kind).

    Before you start

    5 minutes

    You need Docker (Docker Desktop on a Mac: give it 4 CPUs and 8 GB), git, openssl and curl. Apple Silicon, Intel and Linux all work; the scripts detect which one you have.

    1. Clone the repository and create the local secrets. Nothing secret is in git: this generates passwords and a dev-only key pair into secrets/, which git ignores. 
      git clone https://github.com/bubunis/test-sre.git && cd test-sre
bash scripts/init-secrets.sh
      You should see
      created secrets/postgres_password.txt
created secrets/app_db_password.txt
...
secrets ready in ./secrets
    2. Install pinned kind, kubectl and helm for your OS and CPU (checksums verified). Skip any you already have. 
      ./deploy/kind/install-tools.sh
export PATH="$HOME/.local/bin:$PATH"

    Mission 1. Run it with Docker Compose

    5 minutesContainerization

    The quickest way to see the service work: two services, Postgres, Redis and the whole Grafana stack on one Docker network, with only the API published.

    1. Build and start everything. 
      docker compose up -d --build
docker compose ps
      You should see
      NAME                              STATUS
sre-assignment-golang-service-1   Up
sre-assignment-python-service-1   Up
...                               (tempo-init "Exited (0)" is fine)
    2. Get a dev JWT (signed with the dev key, standing in for an identity provider) and ask for a token. 
      JWT=$(bash scripts/dev-token.sh)
curl -s -X POST http://localhost:8000/token \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"user_email": "alice@example.com"}'
      You should see
      {"token":"3f9c…","permissions":["read:data","write:data"]}
    3. Try without a token, and for a user who doesn't exist. 
      curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8000/token -H "Content-Type: application/json" -d '{"user_email":"alice@example.com"}'
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8000/token -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" -d '{"user_email":"nobody@example.com"}'
      You should see
      401
404
    4. Look at how the images are built: multi-stage, non-root, minimal runtime. 
      docker inspect -f '{{.Config.User}}' $(docker compose ps -q golang-service) $(docker compose ps -q python-service)
docker images | grep sre-assignment
      You should see
      65532:65532
10001:10001
    Why. The Go service runs from distroless/static: no shell, no package manager, just the binary, so it checks its own health over gRPC. The Python image builds its virtualenv in one stage and copies only that and the app files into a slim runtime. Passwords reach containers as Docker secrets (files), never as environment variables.
    docker compose down     # free the resources before Mission 2

    Mission 2. Start the Kubernetes cluster

    8 minutesKubernetes

    A kind cluster with one control plane and two workers labelled as two zones. up.sh builds the images for your CPU, loads them into the nodes, creates the Secrets from secrets/, and installs metrics-server, the observability stack and the app.

    1. Bring it up. Pick one mode: 
      ./deploy/kind/up.sh              # plain: helm installs everything (works offline)
# or
GITOPS=1 ./deploy/kind/up.sh     # Argo CD installs everything from GitHub (see Mission 9)
      You should see (last lines)
      NAME                                  READY   STATUS    NODE
token-service-api-7c9…                1/1     Running   token-service-worker
token-service-api-7c9…                1/1     Running   token-service-worker2
token-service-grpc-5d8…               1/1     Running   token-service-worker
token-service-grpc-5d8…               1/1     Running   token-service-worker2
token-service-postgres-0              1/1     Running   token-service-worker2
token-service-redis-0                 1/1     Running   token-service-worker

API: http://127.0.0.1:8080
    2. See the layout: apps only on workers, one replica of each in each zone. 
      kubectl get nodes -L topology.kubernetes.io/zone
kubectl -n token-service get deploy,sts,svc,hpa,pdb
    Why. Three nodes is the smallest layout that still shows zone spreading, PodDisruptionBudgets and node drains, and it fits a laptop and a GitHub runner. Postgres and Redis are StatefulSets; Postgres keeps its data on a PVC.

    Mission 3. Probes, limits, config and service discovery

    5 minutesKubernetes
    1. Run the end-to-end checks: token flow, security settings, zones. 
      ./deploy/kind/smoke.sh
      You should see
      Functional
  PASS  readyz is 200
  PASS  no JWT -> 401
  PASS  alice gets a token
  PASS  token stored in Redis
Cluster layout
  PASS  3 nodes Ready
  PASS  API pods in 2 zones
Security
  PASS  no pod runs as root
  PASS  token_api is not a superuser
...
passed: …  failed: 0
    2. Look at the probes and limits on a Go pod: native gRPC probes, liveness separate from readiness. 
      kubectl -n token-service describe pod -l app.kubernetes.io/name=grpc | grep -E "Liveness|Readiness|Limits|Requests" -A2 | head -20
      You should see
      Limits:    cpu: 250m  memory: 128Mi
Requests:  cpu: 50m   memory: 64Mi
Liveness:  grpc <pod>:50051 liveness  ...
Readiness: grpc <pod>:50051  ...
    3. Configuration: plain settings in ConfigMaps, passwords as files from Secrets. Service names are plain Kubernetes DNS. 
      kubectl -n token-service get configmap token-service-api -o yaml | grep -E "DATABASE_URL|TOKEN_SERVICE_HOST|_FILE"
kubectl -n token-service get secrets
      You should see
      DATABASE_URL: postgres://token_api@token-service-postgres:5432/tokendb
DB_PASSWORD_FILE: /etc/secrets/db/password
TOKEN_SERVICE_HOST: dns:///token-service-grpc:50051
...
token-db   token-jwt   token-redis
    Why. Readiness says "send me traffic" (the API checks the database and the Go service; the Go service checks Redis). Liveness only says "the process isn't stuck", so a Redis outage takes pods out of rotation without restarting them, which wouldn't help. The Go Service is headless and the API load-balances gRPC calls itself (round_robin), because one long-lived HTTP/2 connection would otherwise pin everything to one pod.

    Mission 4. Follow one request: trace and logs

    6 minutesLogging · Tracing
    1. Open the UIs (leave this terminal running) and log in to Grafana as admin with the password from secrets/grafana_admin_password.txt. 
      ./deploy/observability/ui.sh
      You should see
      Grafana:      http://127.0.0.1:3000  (admin / …)
Prometheus:   http://127.0.0.1:9091
Alertmanager: http://127.0.0.1:9093
    2. In a second terminal, send one request. The API returns its trace id in X-Trace-Id. 
      API=http://127.0.0.1:8080 bash scripts/demo-request.sh
      You should see
      POST /token for alice@example.com -> HTTP 200
trace id: 4bf92f3577b34da6a3ce929d0e0e4736

Grafana (http://127.0.0.1:3000) -> Explore:
  Tempo:  4bf92f3577b34da6a3ce929d0e0e4736
  Loki:   {service_name=~"python-token-service|go-token-service"} | trace_id="4bf9…"
    3. Trace: Grafana → Explore → Tempo → paste the trace id. You should see POST /token → the PostgreSQL SELECT → the gRPC call → MintToken in the Go service → Redis set and xadd → process token event from the audit worker, all in one trace.
    4. Logs of that request, from both services: Explore → Loki → paste the Loki query. Every line is JSON with trace_id and span_id, and no email address (it's replaced by a pseudonym like user-ff8d9819fc0e). Click View trace on a line to jump back to Tempo.
    5. Check it all automatically: 
      ./deploy/observability/check.sh
      You should see (part)
      One request, end to end (Tempo + Loki)
  PASS  API returns X-Trace-Id
  PASS  trace includes PostgreSQL
  PASS  trace includes the Go service
  PASS  trace includes Redis
  PASS  Loki: API log lines for this request
  PASS  Loki: Go log lines for this request
...
passed: …  failed: 0
    Why. W3C trace context travels from the API over gRPC into the Go service, and inside the Redis Stream event to the worker, so even the asynchronous part joins the trace. Both services write the same JSON log shape to stdout and send it over OTLP to the collector, which adds pod and namespace labels and masks any email that slips through before Loki stores it.

    Mission 5. Dashboards with live metrics

    5 minutesMetrics
    1. Send realistic traffic for a few minutes (valid callers, unknown users, bad tokens). 
      API=http://127.0.0.1:8080 bash scripts/scenarios.sh baseline 300
    2. Open Dashboards → Token Service → Overview (last 15 minutes): request rate, errors and latency (RED) for /token, availability, which services are up.
    3. Open Dependencies: gRPC rate, errors and p95 by method and code; database pool in use, wait time and timeouts; Redis audit queue depth, pending events and processing time.
    4. The raw series, if you want them in Prometheus (127.0.0.1:9091): 
      sum by (status) (rate(http_requests_total{handler="/token"}[1m]))
db_pool_connections_in_use / db_pool_connections_max
token_events_queue_depth
histogram_quantile(0.95, sum by (le) (rate(token_event_processing_seconds_bucket[5m])))
    Why. RED for every endpoint tells me users are affected; saturation of the pool and the queue tells me what's about to be. The seven dashboards are JSON in git and load the same way in Compose and on Kubernetes.

    Mission 6. Break something

    6 minutesProduction scenarios
    1. Freeze Redis for a minute and watch the Go pods. (Pausing it, rather than scaling it to zero, also works in GitOps mode, where Argo CD would put a scaled-down replica straight back.) 
      kubectl -n token-service exec sts/token-service-redis -- sh -c \
  'REDISCLI_AUTH="$(cat /etc/secrets/redis/password)" redis-cli CLIENT PAUSE 60000 ALL'
kubectl -n token-service get pods -l app.kubernetes.io/name=grpc -w
      You should see
      token-service-grpc-…   0/1   Running   0   …      ← not ready, but RESTARTS stays 0
      On the Dependencies dashboard, mint errors and 5xx climb; /token answers 503 within the 2-second deadline.
    2. After 60 seconds the pause ends and everything recovers on its own: Go pods ready again, /token back to 200.
    3. Or let the script do this and a node drain under load: 
      CHAOS=1 ./deploy/kind/smoke.sh
      You should see (part)
      Resilience: Redis stops answering
  PASS  Go pods become NOT ready
  PASS  /token -> 503 while Redis is down
  PASS  Go pods were not restarted
Resilience: drain a worker (node maintenance / lost zone)
  PASS  drain respects PDBs and finishes
  PASS  /token works with one zone
    Why. Restarting a healthy process can't fix its dependency, so the Go service's liveness ignores Redis and only readiness follows it. PodDisruptionBudgets and maxUnavailable: 0 keep at least one API and Go pod serving during drains and rollouts.

    Mission 7. Who can talk to whom

    4 minutesBonus · Network policies

    The Go service has no authentication of its own: the API checks the JWT and the user. So only the API may reach it.

    1. Run the policy checks. The control proves the real API pod can still mint; the others prove nobody else can. 
      ./deploy/kind/policy-check.sh
      You should see (part)
      Network policies
  PASS  API pod can still mint (control)
  PASS  pod in 'default' can't mint (F1)
  PASS  pod in 'default' can't reach Postgres
  PASS  pod in 'default' can't reach Loki (F9)
    2. See the rules: default deny, then one policy per workload. 
      kubectl -n token-service get networkpolicy
kubectl -n token-service describe networkpolicy token-service-grpc
    Why. Egress is limited too: Postgres and Redis can't call out at all, so a compromised database can't phone home. The next layer would be mTLS between the API and the Go service, so identity doesn't depend on the network alone.

    Mission 8. Autoscaling

    5 minutesBonus · HPA
    1. Watch the autoscalers in one terminal, and send steady load from eight callers in another. 
      kubectl -n token-service get hpa -w
      ./deploy/kind/load.sh
      You should see
      NAME                 TARGETS        MINPODS   MAXPODS   REPLICAS
token-service-api    cpu: 142%/70%  2         5         2  →  4
token-service-grpc   cpu: 81%/70%   2         4         2  →  3
    2. After the load stops, it scales back down slowly (3-minute window), one pod a minute.
    Why. Scale up fast, scale down slowly, so a short lull doesn't drop capacity. The ceiling is chosen against the database: 5 API pods × 10 connections = 50, exactly the token_api login's connection limit. Each caller also has a rate limit, so one client can't take the capacity.

    Mission 9. GitOps with Argo CD

    6 minutesBonus · GitOps
    Needs GitOps mode. Start the cluster with GITOPS=1 ./deploy/kind/up.sh from a pushed branch. Argo CD reads GitHub, not your disk. For a private fork, export GIT_TOKEN=<read-only token> first.
    1. See what Argo CD manages: an app of apps, applied in waves (add-ons, then observability, then the app). 
      kubectl -n argocd get applications
      You should see
      NAME                    SYNC STATUS   HEALTH STATUS
token-platform          Synced        Healthy
metrics-server          Synced        Healthy
observability-config    Synced        Healthy
loki                    Synced        Healthy
tempo                   Synced        Healthy
otel-collector          Synced        Healthy
kube-prometheus-stack   Synced        Healthy
token-service           Synced        Healthy
      The UI is on https://127.0.0.1:8443 while ui.sh runs (user admin; it prints the password).
    2. Drift: change the cluster by hand and watch Argo CD undo it. 
      kubectl -n token-service delete networkpolicy token-service-grpc
sleep 60; kubectl -n token-service get networkpolicy token-service-grpc
      You should see
      NAME                 POD-SELECTOR   AGE
token-service-grpc   …              20s        ← recreated from git
    3. A change through git: raise the API's maximum replicas, push, and watch it arrive (within about a minute). 
      sed -i.bak 's/maxReplicas: 5 /maxReplicas: 6 /' deploy/helm/token-service/values.yaml && rm deploy/helm/token-service/values.yaml.bak
git commit -am "api: allow 6 replicas" && git push
kubectl -n token-service get hpa token-service-api -w
    Why. What's in git is what runs: automated sync with prune and self-heal. Secrets are the exception on purpose: bootstrap.sh creates them from local files (production: External Secrets or Sealed Secrets). CI deploys through the same path, pinned to the commit under test.

    Mission 10. SLOs and alerts

    4 minutesBonus · SLO alerting
    SLISLOAlert
    /token calls without a 5xx99.5% over 30 daysFast burn 14.4× (1 h and 5 m), slow burn 6× (6 h and 30 m)
    /token calls under 0.5 s95%14.4× burn (1 h and 5 m), warning
    1. Open Prometheus → Alerts: the groups token-service-slo.alerts and token-service-dependencies.alerts. Rules are in deploy/helm/token-service/templates/prometheusrule.yaml.
    2. Open Grafana → Dashboards → Token Service → SLOs: SLI and error budget left over the 30-day window, burndown, burn rate per alert window, firing SLO alerts, and the error budget policy.
    3. Check the recorded error ratio: 
      token:request_error_ratio:rate5m
    Challenge: make the fast-burn alert fire

    Keep traffic going, then freeze Redis for ten minutes. Every valid request now fails with 503, so after about five minutes the 1-hour error ratio passes 14.4 × 0.5% = 7.2%, and two minutes later TokenAvailabilityFastBurn turns from pending to firing. The pause ends by itself; the alert clears a few minutes later, thanks to the 5-minute window.

    API=http://127.0.0.1:8080 bash scripts/scenarios.sh baseline 900 &
kubectl -n token-service exec sts/token-service-redis -- sh -c \
  'REDISCLI_AUTH="$(cat /etc/secrets/redis/password)" redis-cli CLIENT PAUSE 600000 ALL'
# watch http://127.0.0.1:9091/alerts (Pending, then Firing after ~7 minutes)
    Why. Alerts are on symptoms users feel, measured against an error budget, so a short blip doesn't page but a steady burn does. The short window in each pair makes the alert stop soon after the problem does. 4xx answers don't count: a bad JWT is the caller's problem.
